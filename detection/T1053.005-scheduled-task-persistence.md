# Detecting Scheduled Task Persistence (T1053.005) with Microsoft Sentinel
**Author:** Shachin P R  
**Date:** 2026-07-26  
**MITRE ATT&CK:** [T1053.005 — Scheduled Task/Job: Scheduled Task](https://attack.mitre.org/techniques/T1053/005/)  
**Tactic:** Persistence  
**Platform:** Windows 11 Pro | Microsoft Sentinel | Azure Arc + AMA

---

## Overview

Scheduled tasks are one of the most common persistence mechanisms used by attackers after gaining initial access. By registering a task that runs at logon, on schedule, or at system startup, an adversary ensures their payload executes automatically — surviving reboots and user logoffs without any further interaction.

This writeup documents the full detection engineering cycle: simulating the technique on a Windows 11 VM, verifying the telemetry reaches Microsoft Sentinel, and building a KQL analytics rule that fires on suspicious task creation.

## Prerequisites

Before EID 4698 (Scheduled Task Created) is logged, the audit policy must be enabled. By default Windows does not log this event.

```powershell
auditpol /set /subcategory:"Other Object Access Events" /success:enable /failure:enable
```

Verify it's active:

```powershell
auditpol /get /subcategory:"Other Object Access Events"
# Expected: Success and Failure
```

> **Note:** This setting resets after a reboot unless enforced via Group Policy. For a persistent lab, configure it through `gpedit.msc → Computer Configuration → Windows Settings → Security Settings → Advanced Audit Policy Configuration`.

## Attack Simulation

The simulation creates a scheduled task named `WindowsUpdateHelper` — a name designed to blend in with legitimate Windows maintenance tasks. It runs `cmd.exe` as SYSTEM at every user logon.

```powershell
schtasks /create `
  /tn "WindowsUpdateHelper" `
  /tr "C:\Windows\System32\cmd.exe /c whoami > C:\Users\Public\out.txt" `
  /sc onlogon `
  /ru SYSTEM `
  /f
```

**What this simulates:**
- An attacker who has gained user-level access creates a task that escalates to SYSTEM on next logon
- The task name mimics a legitimate Windows process to avoid casual inspection
- The trigger (`onlogon`) ensures persistence across reboots

## Telemetry — EID 4698

After the task is created, Windows logs EID 4698 in the Security event log. The raw event contains XML-structured `EventData` with the task name, content, and the account that created it.

In Microsoft Sentinel, querying the `SecurityEvent` table confirms the event arrived:

```kql
SecurityEvent
| where EventID == 4698
| extend TaskName = extract(@"<Data Name=""TaskName"">([^<]+)</Data>", 1, EventData)
| extend SubjectUserName = extract(@"<Data Name=""SubjectUserName"">([^<]+)</Data>", 1, EventData)
| project TimeGenerated, Computer, SubjectUserName, TaskName
```

**Results from the lab:**

| TimeGenerated | Computer | SubjectUserName | TaskName |
|---|---|---|---|
| 2026-07-26 22:15:00 | Target | shach | \WindowsUpdateHelper |
| 2026-07-26 22:06:55 | Target | shach | \WindowsUpdateHelper |

Six events were captured across the session, confirming reliable detection.

## KQL Detection Rule

The detection logic filters out legitimate Windows built-in scheduled tasks (which live under `\Microsoft\`) and flags everything else. This is a simple but effective first-pass filter that catches attacker-created tasks while minimizing noise from Windows itself.

```kql
SecurityEvent
| where EventID == 4698
| extend TaskName = extract(@"<Data Name=""TaskName"">([^<]+)</Data>", 1, EventData)
| extend SubjectUserName = extract(@"<Data Name=""SubjectUserName"">([^<]+)</Data>", 1, EventData)
| where TaskName !startswith @"\Microsoft\"
| project TimeGenerated, Computer, SubjectUserName, TaskName
```

**Logic breakdown:**

| Line | Purpose |
|---|---|
| `where EventID == 4698` | Filter to scheduled task creation events only |
| `extract TaskName` | Parse task name from raw XML EventData |
| `extract SubjectUserName` | Parse the account that created the task |
| `where TaskName !startswith "\Microsoft\"` | Exclude legitimate Windows built-in tasks |
| `project` | Surface only relevant fields for triage |

## Triage Notes

When this rule fires, an analyst should:

1. **Check the task name** — does it resemble a legitimate Windows task? Common red flags: names mimicking Windows components (`WindowsUpdate`, `SystemHealth`, `SvcHost`), random strings, or names with typos
2. **Check the task content** — what command does it run? Look for `cmd.exe`, `powershell.exe`, `wscript.exe`, or paths outside `C:\Windows\System32\`
3. **Check the creating account** — was it created by a standard user, a service account, or SYSTEM? Standard users creating SYSTEM-level tasks is highly suspicious
4. **Correlate with process creation** — search Sysmon EID 1 around the same timestamp for `schtasks.exe` execution to get the full command line
5. **Check task persistence trigger** — `onlogon` and `onstartup` triggers are more suspicious than scheduled time-based triggers

---

## Detection Gaps & Improvements

This rule catches the most common path (EID 4698 via `schtasks.exe`) but has gaps:

- **COM-based task creation** bypasses `schtasks.exe` and may not generate EID 4698 in all configurations — Sysmon EID 1 watching for `taskeng.exe` or `taskhostw.exe` spawning unusual children adds coverage
- **XML task import** via `schtasks /create /xml` can import pre-built task definitions — the task name filter still catches this but the `TaskContent` field would contain the full XML payload and is worth parsing
- **Allowlist tuning** — in a production environment, known-good task names should be added to the exclusion list to reduce false positives from legitimate software

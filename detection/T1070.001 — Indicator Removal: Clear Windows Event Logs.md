# T1070.001 — Indicator Removal: Clear Windows Event Logs
**Author:** Shachin P R  
**Date:** 2026-08-08
**Platform:** Microsoft Sentinel (soc-lab-workspace2)
**Data sources:** Sysmon (via Azure Monitor Agent → WindowsEvent table)
**MITRE ATT&CK:** [T1070.001 — Indicator Removal on Host: Clear Windows Event Logs](https://attack.mitre.org/techniques/T1070/001/)
**Tactic:** Defense Evasion

## Scenario

Simulated an attacker covering their tracks after an intrusion by clearing the Windows Security event log:

```powershell
wevtutil cl Security
```

This is a common last-stage move in an attack chain — remove logon/logoff and privilege-use records before an operator or automated response can review them.

## Initial approach (and why it didn't hold up)

The obvious signal for a log clear is the event Windows itself generates when a log is cleared:

- **Event ID 1102** — "The audit log was cleared" (written to the Security log)
- **Event ID 104** — "The log file was cleared" (written to System/Application logs, classic eventlog provider)

Both looked reasonable on paper, but testing surfaced a structural problem: **the log-clear event is written into the very log that just got cleared.** If there's any delay between the clear operation and the logging pipeline reading that event — buffer timing, agent lag, or (as happened during testing) the clear operation itself disrupting the collection agent's read position — the detection event can be lost along with everything else in the log. Relying on 1102/104 as the *only* signal means the detection can fail silently in exactly the scenario it's meant to catch.

## Final detection: catch the tool execution, not the log record

Instead of watching the log that gets wiped, the detection watches **Sysmon Event ID 1 (Process Creation)** — a completely separate telemetry stream that isn't affected by anything happening to the Security log. Any execution of `wevtutil.exe` with a clear (`cl`) argument gets caught upstream of the log clear itself.

### KQL Query

```kql
WindowsEvent
| where tostring(EventID) == "1"
| extend parsed = parse_json(EventData)
| extend Image = tostring(parsed.Image), CommandLine = tostring(parsed.CommandLine)
| where Image has "wevtutil.exe" and CommandLine has_any ("cl ", "clear-log")
| project TimeGenerated, Computer, Image, CommandLine
```

### Result

Confirmed hit on test execution:

| TimeGenerated | Computer | Image | CommandLine |
|---|---|---|---|
| 2026-08-08T11:12:51.665Z | Target | C:\Windows\System32\wevtutil.exe | "C:\WINDOWS\system32\wevtutil.exe" cl Security |

## Key takeaways

1. **Don't detect on the artifact an attacker is actively destroying.** 1102/104 are legitimate corroborating signals, but they live inside the blast radius of the technique itself. A detection that depends on the thing being attacked surviving the attack is fragile by design.
2. **Prefer upstream telemetry that's structurally independent of the target.** Sysmon process-creation logging happens *before* the log clear takes effect and writes to a different channel entirely — it can't be erased by the same action that clears Security.
3. **This generalizes.** The same "detect the tool, not the trace" principle applies to other log-tampering and evidence-destruction techniques (e.g., clearing PowerShell history, deleting shadow copies) — command-line/process telemetry is often more resilient than the artifact the attacker is trying to destroy.

## Notes / lessons from the lab environment

- `wevtutil cl Security` disrupts the local AMA agent's read position on the Security log, which can break `SecurityEvent` ingestion for a period afterward — a good reminder that log-clearing techniques can have side effects on defensive tooling itself, not just on visibility.
- Tested with a single execution; repeated clears during troubleshooting were avoided after the first test confirmed the pipeline impact.

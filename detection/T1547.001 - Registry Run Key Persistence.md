# Detecting Registry Run Key Persistence (T1547.001) with Microsoft Sentinel
**Author:** Shachin P R  
**Date:** 2026-08-01  
**MITRE ATT&CK:** [T1547.001 — Boot or Logon Autostart Execution: Registry Run Keys](https://attack.mitre.org/techniques/T1547/001/)  
**Tactic:** Persistence  
**Platform:** Windows 11 Pro | Microsoft Sentinel | Sysmon EID 13

---

## Overview

Registry Run keys are one of the oldest and most widely abused persistence mechanisms in Windows. When a value is written to `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` or its variants, Windows automatically executes that command every time the user logs in. Attackers use this to survive reboots without requiring elevated privileges — a standard user can write to `HKCU` with no admin rights whatsoever.

This writeup covers the full detection cycle: simulating the technique, confirming telemetry in Sentinel via Sysmon EID 13, writing a KQL detection rule using `parse_json()`, and deploying it as an analytics rule in the Defender portal.

## Key Registry Persistence Locations

| Key | Scope | Privilege Required |
|---|---|---|
| `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` | Current user only | Standard user |
| `HKCU\Software\Microsoft\Windows\CurrentVersion\RunOnce` | Current user, runs once | Standard user |
| `HKLM\Software\Microsoft\Windows\CurrentVersion\Run` | All users | Administrator |
| `HKLM\Software\Microsoft\Windows\CurrentVersion\RunOnce` | All users, runs once | Administrator |

`HKCU` keys are particularly dangerous because they require no elevation — any user-level payload can establish persistence this way.

## Sysmon Configuration Requirement

Sysmon must have `RegistryEvent` logging enabled. The config used in this lab:

```xml
<Sysmon schemaversion="4.90">
  <EventFiltering>
    <RuleGroup name="" groupRelation="or">
      <RegistryEvent onmatch="exclude">
      </RegistryEvent>
    </RuleGroup>
  </EventFiltering>
</Sysmon>
```

`onmatch="exclude"` with no rules means log everything — no filtering. Apply with:

```powershell
sysmon64 -c "C:\Windows\sysmon-config.xml"
```

## Attack Simulation

The simulation adds a Run key named `WindowsUpdateService` — again using a name that blends in with legitimate Windows components:

```powershell
reg add "HKCU\Software\Microsoft\Windows\CurrentVersion\Run" `
  /v "WindowsUpdateService" `
  /t REG_SZ `
  /d "C:\Windows\System32\cmd.exe /c whoami > C:\Users\Public\out.txt" `
  /f
```

**What this simulates:**
- Attacker with standard user access establishes logon persistence
- No admin rights required — `HKCU` is writable by any user
- Value name mimics a Windows service to avoid casual inspection
- Payload executes `cmd.exe` at every user logon

## Telemetry — Sysmon EID 13

Sysmon EID 13 (RegistryEvent — Value Set) fires immediately when the registry key is written. Unlike Windows native auditing (EID 4657), Sysmon EID 13 requires no SACL configuration on the registry key — it captures all registry writes automatically based on the Sysmon config.

Sysmon stores registry events in the `WindowsEvent` table in Sentinel with EventData in JSON format. The key fields:

| Field | Value |
|---|---|
| EventType | SetValue |
| TargetObject | Full registry path including value name |
| Details | The data written to the value |
| Image | Process that made the change |
| User | Account that triggered it |

## KQL Detection Rule

The `WindowsEvent` table stores Sysmon EventData as a JSON string. Using `parse_json()` to extract fields is more reliable than regex in Sentinel for structured JSON payloads:

```kql
WindowsEvent
| where Provider == "Microsoft-Windows-Sysmon"
| where tostring(EventID) == "13"
| where EventData contains "CurrentVersion\\Run"
    or EventData contains "CurrentVersion\\RunOnce"
| extend parsed = parse_json(EventData)
| extend TargetObject = tostring(parsed.TargetObject)
| extend Details = tostring(parsed.Details)
| extend User = tostring(parsed.User)
| extend Image = tostring(parsed.Image)
| project TimeGenerated, Computer, User, Image, TargetObject, Details
```

**Logic breakdown:**

| Line | Purpose |
|---|---|
| `where Provider == "Microsoft-Windows-Sysmon"` | Filter to Sysmon events only |
| `where tostring(EventID) == "13"` | RegistryEvent — Value Set |
| `where EventData contains "CurrentVersion\\Run"` | Target the Run/RunOnce persistence keys |
| `parse_json(EventData)` | Parse the JSON EventData payload |
| `extend TargetObject/Details/User/Image` | Extract key fields for triage |

**Confirmed results from lab:**

| Field | Value |
|---|---|
| Computer | Target |
| User | Target\shach |
| Image | C:\WINDOWS\system32\reg.exe |
| TargetObject | HKU\S-1-5-...\CurrentVersion\Run\WindowsUpdateService |
| Details | C:\Windows\System32\cmd.exe /c whoami > C:\Users\Public\out.txt |

## Why parse_json() Instead of extract()

In Sentinel's KQL implementation, the `extract()` function does not support regex patterns containing double-quote characters — even with `@` verbatim string prefix. Since Sysmon EventData in the `WindowsEvent` table is stored as JSON (not XML like in the `SecurityEvent` table), `parse_json()` is both simpler and more reliable:

```kql
// This fails in Sentinel:
extend TargetObject = extract(@'"TargetObject":"([^"]+)"', 1, EventData)

// This works:
extend parsed = parse_json(EventData)
extend TargetObject = tostring(parsed.TargetObject)
```

This is a key difference between Sysmon events in `WindowsEvent` vs Windows native events in `SecurityEvent` — SecurityEvent uses XML EventData requiring `extract()` with double-escaped patterns, while WindowsEvent uses JSON allowing `parse_json()`.

## Triage Notes

When this rule fires:

1. **Check TargetObject** — is the value name suspicious? Legitimate software uses specific names. Random strings, names mimicking Windows components (`WindowsUpdate`, `SecurityHealth`, `SvcHost`), or unexpected vendor names are red flags
2. **Check Details (the value data)** — what command is being persisted? `cmd.exe`, `powershell.exe`, `wscript.exe`, paths in `%TEMP%` or `%APPDATA%`, or encoded commands are highly suspicious
3. **Check Image** — what process wrote the key? `reg.exe` and `regedit.exe` are common legitimate tools but also common attacker tools. PowerShell writing directly to the registry via `Set-ItemProperty` is also common and won't show `reg.exe`
4. **Check User** — standard user accounts creating Run keys are more suspicious than admin accounts or software installers
5. **Timeline correlation** — search for Sysmon EID 1 (process creation) around the same timestamp to find what spawned `reg.exe` and get the full attack chain

## Detection Gaps & Improvements

- **HKLM Run keys** require admin rights but are also covered by this rule since we filter on `CurrentVersion\\Run` which matches both HKCU and HKLM paths
- **PowerShell direct registry writes** via `New-ItemProperty` or `Set-ItemProperty` show `powershell.exe` as the Image — covered by this rule
- **COM-based registry writes** from malicious DLLs may show a legitimate host process (e.g. `explorer.exe`, `svchost.exe`) as the Image — requires additional process injection detection
- **Allowlisting** — known software installers (e.g. Teams, Slack, OneDrive) write to Run keys legitimately. In production, filter these by `Image` path or `TargetObject` value name to reduce false positives
